# The Grepr data lake

Grepr pipelines use a data lake deployed on Amazon S3 to store data, including raw logs and metadata, across different processing stages. The metadata stored in the data lake can include patterns identified during log message processing or message identifiers. You can also choose to save the processed output events from your pipelines in the data lake.

The data lake uses [Apache Iceberg](https://iceberg.apache.org/) and [Apache Parquet](https://parquet.apache.org/) to create a storage layer optimized for storing and querying large datasets. Both Iceberg and Parquet are open-source projects that are widely used to support data engineering workloads.

Iceberg is a table format designed to store and query large datasets efficiently. Parquet is a column-oriented storage format designed for efficient data storage and retrieval. The Grepr data lake stores data in Parquet files, and Iceberg manages them as tables. The combination of Iceberg and Parquet provides efficient data storage and support for database-like functionality, including queries, transactions, and schema evolution.

Although you configure each of your pipelines with a single data lake, an S3 bucket can host multiple data lakes. In the data lake, Grepr stores data in _datasets_. A Grepr dataset defines a namespace in the data lake that identifies where specific data is stored and isolates that data from other datasets.

An example of a dataset is the one you add to a pipeline to capture the pipeline's output. However, a dataset is not restricted to a single pipeline: You can create a dedicated dataset for a single pipeline or configure multiple pipelines to use a shared dataset.

## How does Grepr use the data lake?

Grepr uses the data stored in the data lake for tasks such as querying raw data or performing backfills. To limit the amount of data required for scans and the associated costs, you should be as precise as possible when you run queries against this data. For example, limit the amount of data scanned by using tags and limited time ranges.

<Callout type="info">
  By default, Grepr sets the following limits for queries against data lake tables:

  - 1 TiB for the amount of data that can be scanned in a single query.
  - A timeout of 10 minutes. The Grepr platform terminates queries that exceed this time limit.

  Although these limits are sufficient for most queries, if your workloads require raising these limits, contact [support@grepr.ai](mailto:support@grepr.ai).
</Callout>

## How is a Grepr data lake deployed?

Because the Grepr platform manages the deployment of the data lake infrastructure, including creation of the required tables and other structures, you don't need to take additional steps to install or configure Iceberg or Parquet. When you add a data lake in the pipelines UI, you only need to configure a storage integration with S3, either using a Grepr-hosted S3 bucket or a self-hosted S3 bucket. To learn how to create and configure an S3 bucket and Grepr storage integration, see [Host a Grepr data lake with the Amazon S3 integration](/integrations/aws-s3).

When you use the API to configure a pipeline, the Grepr platform also manages the deployment of the tables and other structures required by the data lake. However, your pipeline configuration must include specific values related to Iceberg sources and sinks. To learn more, see [Create and manage jobs with the Grepr REST API](/apis/job-creation-guide).

## Store distribution metrics in less space [#distribution-sketch-cap]

When a metrics pipeline writes distribution metrics, such as the Datadog Agent's, to its lake, the lake stores each point's count, sum, average, minimum, and maximum. The lake's _distribution storage_ sets what else it keeps of each point's sketch, which decides the percentiles you can query and the space each point takes:

| Distribution storage | Also stored for each point | Percentiles you can query | Bytes per point |
|---|---|---|---|
| **Summary only** | Nothing | None | 32 |
| **Summary and p50, p90, p95, p99** | Its p50, p90, p95, and p99 | Each point's stored percentiles, and their highest across points | 37 |
| **T-digest** | Its sketch as a _t-digest_ | Any percentile, of one point or of points merged | 185, or 111 with a cap of 32 centroids |

The bytes are after compression, measured on a synthetic mix of distribution points.

To choose a pipeline's distribution storage, open the metrics pipeline, click **Lake** in the left pane, select an option under **Distribution storage**, and click **Apply Changes**. A lake you add in the pipeline editor starts on **Summary and p50, p90, p95, p99**. A lake whose pipeline doesn't set distribution storage, such as one added before Grepr offered the setting, stores t-digests with no cap.

### Query stored percentiles [#stored-percentiles]

Each stored percentile is the value of the sketch bin that holds it, within about 1.6% of the point's own percentile. Grepr SQL reads them as the `sketch_p50`, `sketch_p90`, `sketch_p95`, and `sketch_p99` columns of the metrics table.

To chart a percentile across points, such as a minute's points from every host, use the highest stored value: in Metrics Explorer, select **p99 stored (max)**, which is `MAX(sketch_p99)`. It reads only the points stored with percentiles. Over those points, the highest stored p99 is at most about 1.6% below the p99 of all their values combined, and it's often far above it, because it's one point's own. On a synthetic workload of 1,000 values a point, it was a median 52% above. To query a percentile of all the points' values combined, store t-digests.

### Cap the size of t-digests [#t-digest-cap]

A t-digest is a list of _centroids_, each a value and the number of the point's values near it, and queries read t-digests to compute percentiles. By default, a t-digest keeps one centroid for each bin of the sketch, so it holds every bin that was sent.

To store t-digests in less space, cap their centroids: in the pipeline's **Lake** step, with **Distribution storage** set to **T-digest**, select a cap under **T-digest cap**, such as **At most 64 centroids**, and click **Apply Changes**. The editor offers caps of 32, 64, 128, 256, 512, 1,024, 2,048, and 4,096 centroids, or **No cap**. Through the API or Terraform, a cap can be any whole number from 32 to 4,096.

When a sketch has more bins than the cap, Grepr merges neighboring centroids until the t-digest has at most the cap, so it takes fewer bytes and gives less precise percentiles. A sketch with as many bins as the cap or fewer is stored the same as with no cap. Each centroid takes 16 bytes before compression. For example, a point whose sketch has 200 bins takes 3,237 bytes with no cap, at most 1,061 bytes with a cap of 64, and at most 549 bytes with a cap of 32.

A cap doesn't change the smallest and largest values. Other percentiles move, and the tail percentiles, such as p99, move the most. Grepr measured how far on synthetic sketches of 1 to 373 bins, compared with no cap. Taking p50, p90, and p99 each on its own, a cap of 64 or more moved 99% of points' p50 by at most 1.7%, their p90 by at most 2.7%, and their p99 by at most 7.7%, and a cap from 32 to 63 moved them by at most 4.2%, 5.8%, and 20.5%. A single point's p99 can move by more when it falls near the point's largest values. Percentiles over many points, such as a chart's time bucket across a metric's hosts, move much less: over 40 hosts and a minute, a cap of 32 moved p50, p90, and p99 by at most 1.1%, 1.6%, and 4.2%, and a cap of 64 by at most 0.6%, 0.9%, and 2.1%.

### Change a pipeline's distribution storage [#change-storage]

A change applies to the points that the pipeline writes after it:

- A running pipeline applies it within 30 seconds, without a restart.
- Points already written keep what they were stored with. Switching to t-digests doesn't add t-digests to earlier points, and raising or removing a cap doesn't restore the precision of points written under a lower cap.

After a change, a dataset holds points stored in more than one way, and each query reads the points that have what it needs. Average, minimum, maximum, sum, and count read every point. A percentile of a distribution, such as **p99 of a distribution**, reads the points stored with t-digests, and a stored percentile reads the points stored with percentiles. A group with none of the points a query reads shows no value.

To set the distribution storage through the API, set `sketchMode` to `SUMMARY`, `PERCENTILES`, or `T_DIGEST` in the metrics pipeline's template input, beside `datasetId`. For `T_DIGEST`, set `sketchMaxCentroids` to a whole number from 32 to 4,096 to cap the t-digests, or leave it out or set it to `0` for no cap. A pipeline whose input leaves out `sketchMode` stores t-digests. In Terraform, set them in the template input of the `grepr_pipeline` resource's `job_graph_json`. See [Configure a metrics pipeline with the API or Terraform](/pipelines/metrics-pipelines#api) and [_](/admin/terraform-provider).

### Store chosen metrics another way [#storage-by-metric]

To store some metrics differently from the rest of the lake, such as keeping t-digests of the latency metrics you chart by percentile in a lake that stores percentiles, add _overrides_ by metric name. Each override has a metric name, a distribution storage, and, for **T-digest**, a cap. Each distribution point takes the storage and cap of the first override that matches its metric's name. A point whose metric matches no override takes the lake's **Distribution storage** and **T-digest cap**.

To add an override, open the metrics pipeline, click **Lake** in the left pane, and under **Storage by metric**, click **Add override**. A new override stores t-digests at the lake's cap. Enter the metric name, select a storage and, for **T-digest**, a cap, and click **Apply Changes**. Use the arrows beside each override to put the more specific ones first. A lake has at most 100 overrides.

An override's metric name matches as follows:

- A name is a glob, where `*` matches any run of characters, such as `http.server.*`. A name without `*` matches exactly one metric.
- A name that starts with `r/` is an [RE2 regular expression](https://github.com/google/re2/wiki/Syntax) that matches the whole metric name, such as `r/(db|cache)\..+`.
- Matching is case-sensitive, against the metric's name after any [renames](/pipelines/metrics-pipelines#source).

An override's **Cap** starts on the lake's, the first option, which shows the lake's **T-digest cap** and follows it when you change it. The lake's cap applies even when the lake's own storage isn't **T-digest**, so it caps the overrides' t-digests in a lake that stores percentiles. To give an override a cap of its own, select a cap or **No cap**.

A change to the overrides applies as a change to the lake's distribution storage does: a running pipeline applies it within 30 seconds, and points already written keep what they were stored with.

To chart a percentile of a metric in Metrics Explorer, select the preset that reads the metric's storage, which is its first matching override's or, when none matches, the lake's. For a metric stored with percentiles, select **p99 stored (max)**. For a metric stored as t-digests, select **p99 of a distribution**. A metric stored as **Summary only** has no percentile to chart.

To set overrides through the API or Terraform, set `sketchOverrides` in the template input, beside `sketchMode`. It's a list of overrides in order. Each has a `metricName` of at most 1,000 characters, a `mode` of `SUMMARY`, `PERCENTILES`, or `T_DIGEST`, and, for `T_DIGEST`, an optional `maxCentroids`: `0` for no cap, or a whole number from 32 to 4,096. Leave out `maxCentroids` to use the lake's cap. For example, the following input stores percentiles, uncapped t-digests for the `http.server.*` metrics, and the summary alone for the metrics whose names start with `db.` or `cache.`:

```json copy
{
  "datasetId": "<your-dataset-id>",
  "sketchMode": "PERCENTILES",
  "sketchOverrides": [
    { "metricName": "http.server.*", "mode": "T_DIGEST", "maxCentroids": 0 },
    { "metricName": "r/(db|cache)\\..+", "mode": "SUMMARY" }
  ]
}
```

The template input's other fields are left out of the example.
