# Configure connections to OpenTelemetry-compatible platforms

The Grepr OpenTelemetry integration enables you to ingest telemetry data into Grepr from a collector that supports the OpenTelemetry Protocol over HTTP, or OTLP/HTTP, process the data with a Grepr pipeline, and then send the processed data to any observability vendor that accepts OTLP/HTTP requests. The OpenTelemetry integration supports logs and Application Performance Monitoring (APM) data, including traces and metrics.

To send logs or APM data to a Grepr pipeline for processing, change your collector configuration to send them to a Grepr endpoint URL instead of your vendor's OTLP/HTTP endpoint. The Grepr OpenTelemetry integration works with any collector that supports OTLP/HTTP, including the OpenTelemetry Collector and Fluent Bit.

The Grepr endpoint URL requires a Grepr-generated token for authentication. When you create an OpenTelemetry integration, Grepr automatically generates this token. In the UI, the token is displayed in a dialog after you create the integration. You must copy this token and include it in your collector configuration. When you use the REST API to create the integration, the token is returned in the response.

You can use the Grepr UI or REST API to add an OpenTelemetry integration. To learn how to create an OpenTelemetry integration in the Grepr UI and configure collectors to send data to Grepr, see [_](#use-opentelemetry-integration). To learn how to configure OpenTelemetry-compatible vendor integrations, see [Use an OTLP/HTTP compatible vendor integration in a Grepr pipeline](#vendor-otel-configuration).

To use the REST API, see the [OpenTelemetry Integration specification](/apis/api-spec#tag/OpenTelemetry-Integration).

## Requirements

Creating and configuring an OpenTelemetry integration requires the URL of the HTTP/HTTPS endpoint where your observability vendor accepts OpenTelemetry data.

## Use an OpenTelemetry integration in a Grepr pipeline [#use-opentelemetry-integration]

Use the following steps to create an OpenTelemetry integration in the Grepr UI and use the integration as a source and sink in a pipeline.

### Step 1: Create an OpenTelemetry integration [#step1-create-integration]

To create an OpenTelemetry integration in the Grepr UI:

1. Go to the **Integrations** page in the Grepr UI and click **Add new** next to **Observability Vendors**.

   ![The Integrations page in the Grepr UI.](/images/tutorials/first-pipeline/integrations-page.png)

1. In the **Add Observability Vendor** dialog:
   - In the **Type** menu, select **Open Telemetry**.
   - In the **Name** field, enter a name for the integration.
   - In the **Endpoint** field, enter the URL for the HTTP/HTTPS endpoint.
   - Optional: To add any required headers, for example, authentication headers such as `Authorization: Bearer <token>` or `X-API-Key: <api-key>`:
     - In the **HTTP Headers** section, click **Add Header** to open the **Add New Header** card.
     - To use a fixed value for the header, in the **Source** menu, select **Static Value** and enter the **Header Name** and **Header Value**.
     - To set the header value using an attribute from processed log events, in the **Source** menu, select **From Attribute**, enter the **Header Name** and **Attribute Path**.
     - To store the value securely and mask it in the UI, click the lock icon. Use this option for all sensitive values, such as API keys or tokens.
     - Click **Save**.
1. Click **Create**.
1. After clicking **Create**, the **Grepr Token** dialog appears with a Grepr-generated token. Click the **Copy to Clipboard** icon to copy the token. This token is required when you configure your collector to send data to Grepr.
1. Click **Confirm** to close the dialog.

   #### Optional: Grant team access to the integration

   <AddTeamAccess />

When you select **From Attribute** to set a header value, Grepr groups log events that share the same attribute value into the same outbound request, sets the header to that value, and forwards the events to your vendor's endpoint. Events with different values for the attribute are sent in separate requests with the corresponding header values. Use this option when downstream routing or tenancy depends on a per-log value, such as a Kubernetes namespace or a tenant identifier.

If a log event does not have the configured attribute, or the attribute value fails Grepr's validation, for example, because it contains control characters or exceeds the maximum length, Grepr delivers the event but omits the header from the request.

You can add both static and attribute-sourced headers to the same integration. Grepr merges them on each outbound request.

### Step 2: Add a source to your pipeline

To add a source to your pipeline that uses the OpenTelemetry integration, select the integration when you create a pipeline. For an existing pipeline, go to the pipeline details page and in the left-hand navigation menu, click **Sources** and select the integration.

### Step 3: Configure forwarding to Grepr [#configure-forwarding-to-grepr]

<IngestUrlConfig image_url='/images/integrations/ingestion-url-otel.png' url='https://<integration-id>-<org-id>.ingest.grepr.ai/otlp/<grepr-token>' />

Replace `<grepr-token>` with the token generated when you created the OpenTelemetry integration in Step 1. The token is part of the ingestion URL rather than a separate credential, so a collector or agent that sends to this URL needs no authentication header.

Some senders take the ingestion URL as it is and append the path for each signal themselves. Others need the full path for one signal. For example, if your ingestion URL is `https://YWNQbQSarRBsa-<org-id>.ingest.grepr.ai/otlp/uUasjYpMJdpQZ9cNlLEtthuXNRp6n3ND_xND80PVXNk=`, then the endpoint for log events is that URL followed by `/v1/logs`, and the endpoint for spans is the same URL followed by `/v1/traces`. Each tab below states which form its sender expects.

To see configuration examples for sending data to Grepr, select the tab for your collector or coding agent:

<Tabs items={['OTel Collector (logs)', 'OTel Collector (traces)', 'Fluent Bit', 'Claude Code', 'Codex', 'OpenCode']}>
  <Tabs.Tab>

    The OpenTelemetry Collector can send logs to Grepr using the `otlphttp` exporter. In the OpenTelemetry collector configuration, set the endpoint to the ingestion URL from your OpenTelemetry integration:

    ```yaml copy filename="config.yaml"
    exporters:
      otlphttp:
        endpoint: <ingestion-url>

    service:
      pipelines:
        logs:
          receivers: [otlp]
          processors: [batch]
          exporters: [otlphttp]
    ```

    Replace `<ingestion-url>` with the ingestion URL from your OpenTelemetry integration.

    For dual shipping, you need to create two exporters: one to send logs to Grepr, and another to send logs directly to your vendor's platform. Your exporter for Grepr only includes Grepr's ingestion endpoint, with any needed headers configured in the Grepr UI. Your exporter for the vendor's platform includes the vendor's endpoint and the necessary headers.

    ```yaml copy filename="config.yaml"
    exporters:
      otlphttp/grepr:
        endpoint: <ingestion-url>

      otlphttp/vendor:
        endpoint: <vendor-otlp-endpoint>
        headers:
          authorization: "Bearer <vendor-token>"

    service:
      pipelines:
        logs:
          receivers: [otlp]
          processors: [batch]
          exporters: [otlphttp/grepr, otlphttp/vendor]
    ```

    Replace:
    - `<ingestion-url>` with the ingestion URL from your OpenTelemetry integration.
    - `<vendor-otlp-endpoint>` with your vendor's OTLP/HTTP endpoint URL.
    - `<vendor-token>` with your vendor's authentication token.

    To learn more about configuration settings for the OpenTelemetry Collector, see the [OTLP/HTTP Exporter documentation](https://github.com/open-telemetry/opentelemetry-collector#readme).

  </Tabs.Tab>

  <Tabs.Tab>

    Similar to log forwarding, the OpenTelemetry Collector can send APM events to Grepr using the `otlphttp` exporter. In your collector configuration, add a `traces` pipeline that uses the `otlphttp` exporter. The exporter appends the path `/v1/traces` to the ingestion URL.

    ```yaml copy filename="config.yaml"
    exporters:
      otlphttp:
        endpoint: <ingestion-url>

    service:
      pipelines:
        logs:
          receivers: [otlp]
          processors: [batch]
          exporters: [otlphttp]
        traces:
          receivers: [otlp]
          processors: [batch]
          exporters: [otlphttp]
    ```

    Replace `<ingestion-url>` with the ingestion URL from your OpenTelemetry integration.

  </Tabs.Tab>

  <Tabs.Tab>

    Fluent Bit can forward logs to Grepr using the OpenTelemetry output plugin. To configure the plugin:

    - Set the `host` value using only the hostname of the ingestion URL from your OpenTelemetry integration, omitting the `https://` prefix and the path value.
    - Set the `logs_uri` value to the ingestion URL path and append `/v1/logs`.

    For example, if your ingestion URL is `https://YWNQbQSarRBsa-<org-id>.ingest.grepr.ai/otlp/uUasjYpMJdpQZ9cNlLEtthuXNRp6n3ND_xND80PVXNk=`, set the `host` value to `YWNQbQSarRBsa-<org-id>.ingest.grepr.ai` and the `logs_uri` value to `/otlp/uUasjYpMJdpQZ9cNlLEtthuXNRp6n3ND_xND80PVXNk=/v1/logs`. The following is an example `OUTPUT` configuration for the OpenTelemetry plugin from a Fluent Bit configuration file (`fluent-bit.conf`):

    ```fluent copy filename="fluent-bit.conf"
    [OUTPUT]
      name                 opentelemetry
      match                *
      host                 <integration-id>-<organization-id>.ingest.grepr.ai
      port                 443
      logs_uri             /otlp/<grepr-token>/v1/logs
      tls                  On
      tls.verify           On
    ```

    To learn more about configuration settings for Fluent Bit, see the documentation for the [Fluent Bit OpenTelemetry output plugin](https://docs.fluentbit.io/manual/data-pipeline/outputs/opentelemetry).

  </Tabs.Tab>

  <Tabs.Tab>

    Claude Code exports its own telemetry over OTLP. It reports prompts, assistant responses, tool calls, token counts, and cost as OTLP log events, and reports each interaction, model request, and tool execution as OTLP spans. An agent sessions pipeline reads both signals, so set a logs endpoint and a traces endpoint.

    - `CLAUDE_CODE_ENABLE_TELEMETRY` turns on telemetry and is required.
    - `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` turns on spans. Without it, Claude Code exports no traces, and a session has no execution spans and no timing waterfall.
    - `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES`, and `OTEL_LOG_TOOL_DETAILS` record prompt text, response text, and tool arguments. Without them, Claude Code redacts the content and a transcript shows metadata only.
    - `OTEL_LOG_TOOL_CONTENT` records what each tool returned. Claude Code reports tool output only on a span event, so this setting requires spans.
    - `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` and `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` each take the full path for their signal, so append `/v1/logs` and `/v1/traces` to the ingestion URL.
    - `OTEL_METRICS_EXPORTER` is set to `none` because an agent sessions pipeline reads logs and traces only.

    The following example exports the settings and then starts Claude Code:

    ```bash copy filename="claude-code-telemetry.sh"
    export CLAUDE_CODE_ENABLE_TELEMETRY=1
    export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
    export OTEL_LOGS_EXPORTER=otlp
    export OTEL_TRACES_EXPORTER=otlp
    export OTEL_METRICS_EXPORTER=none
    export OTEL_EXPORTER_OTLP_LOGS_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=<ingestion-url>/v1/logs
    export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=<ingestion-url>/v1/traces
    export OTEL_LOG_USER_PROMPTS=1
    export OTEL_LOG_ASSISTANT_RESPONSES=1
    export OTEL_LOG_TOOL_DETAILS=1
    export OTEL_LOG_TOOL_CONTENT=1

    claude
    ```

    Replace `<ingestion-url>` with the ingestion URL from your OpenTelemetry integration.

    <Callout type="info">
      Claude Code truncates prompts, responses, and tool content at 60 KB. Grepr labels shortened content as a truncated capture in the transcript. To raise the limit, set `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH` to a larger value.
    </Callout>

    To learn more about the settings Claude Code supports, see [Monitoring usage](https://code.claude.com/docs/en/monitoring-usage).

    To learn what an agent session contains and how to build the pipeline that captures one, see [Capture and explore agent sessions](https://docs.grepr.ai/pipelines/agent-sessions).

  </Tabs.Tab>

  <Tabs.Tab>

    Codex exports its own telemetry over OTLP. It reports prompts, tool results, and token counts as OTLP log events named `codex.*`, and reports turns, model responses, and command executions as OTLP spans. Codex selects a separate exporter for each signal, so configure both.

    - `otel.exporter` selects the exporter for log events.
    - `otel.trace_exporter` selects the exporter for spans. Without it, Codex exports no spans, and a session has no execution spans and no timing waterfall.
    - Each endpoint must include the path for its signal, `/v1/logs` for log events and `/v1/traces` for spans. Codex sends to the endpoint you configure without appending a path.
    - `otel.metrics_exporter` is set to `none` because an agent sessions pipeline reads logs and traces only. The default sends metrics to Statsig.
    - `otel.log_user_prompt` records prompt text. Without it, Codex omits the prompt and a transcript shows metadata only.

    The following example is a snippet from the Codex configuration file, `~/.codex/config.toml`:

    ```ini copy filename="config.toml"
    [otel]
    environment = "production"
    log_user_prompt = true
    metrics_exporter = "none"

    [otel.exporter.otlp-http]
    endpoint = "<ingestion-url>/v1/logs"
    protocol = "binary"

    [otel.trace_exporter.otlp-http]
    endpoint = "<ingestion-url>/v1/traces"
    protocol = "binary"
    ```

    Replace `<ingestion-url>` with the ingestion URL from your OpenTelemetry integration.

    <Callout type="info">
      Codex reports a different service name for each of its binaries, `codex_exec` when you run `codex exec` and `codex_cli_rs` when you run the interactive CLI. Grepr recognizes both, so sessions from either binary appear together.
    </Callout>

    To learn more about the settings Codex supports, see the [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

    To learn what an agent session contains and how to build the pipeline that captures one, see [Capture and explore agent sessions](https://docs.grepr.ai/pipelines/agent-sessions).

  </Tabs.Tab>

  <Tabs.Tab>

    OpenCode reports agent activity through an OpenTelemetry plugin, which exports prompts, assistant responses, tool calls, tool results, token counts, and cost as OTLP spans. Register the plugin in your OpenCode configuration and then point it at your ingestion URL.

    - The `plugin` array in your OpenCode configuration loads `@devtheops/opencode-plugin-otel`. Pin the version so a later release cannot change what the plugin reports.
    - `OPENCODE_ENABLE_TELEMETRY` turns on the plugin's export and is required.
    - `OPENCODE_OTLP_ENDPOINT` is the ingestion URL without a signal path. The plugin appends the path itself.
    - `OPENCODE_DISABLE_LOGS` stops the plugin exporting log records. The plugin reports a whole session on spans, so its log records are not part of an agent session.
    - Leave the standard `OTEL_` variables unset. They turn on OpenCode's built-in instrumentation, which reports internal runtime operations such as `sql.execute` rather than agent activity.

    The following example registers the plugin, exports the settings, and then starts OpenCode:

    ```bash copy filename="opencode-telemetry.sh"
    cat > opencode.json <<'JSON'
    {
      "plugin": ["@devtheops/opencode-plugin-otel@1.4.0"]
    }
    JSON

    export OPENCODE_ENABLE_TELEMETRY=1
    export OPENCODE_OTLP_ENDPOINT=<ingestion-url>
    export OPENCODE_OTLP_PROTOCOL=http/protobuf
    export OPENCODE_DISABLE_LOGS=1

    opencode
    ```

    Replace `<ingestion-url>` with the ingestion URL from your OpenTelemetry integration.

    <Callout type="info">
      The plugin also exports metrics, which an agent sessions pipeline does not read. To stop exporting them, set `OPENCODE_DISABLE_METRICS` to a comma-separated list of the metric names you want to disable. The setting matches each name exactly and has no single value that disables all of them.
    </Callout>

    To learn what an agent session contains and how to build the pipeline that captures one, see [Capture and explore agent sessions](https://docs.grepr.ai/pipelines/agent-sessions).

  </Tabs.Tab>
</Tabs>

## Use an OTLP/HTTP compatible vendor integration in a Grepr pipeline [#vendor-otel-configuration]

The following tabs show the integration configurations required to connect Grepr to an observability vendor's OTLP/HTTP endpoint. To connect to a vendor not listed here:

1. In your vendor's documentation, find their OTLP/HTTP endpoint URL and any required authentication headers.
1. Create an OpenTelemetry integration in Grepr using your vendor's endpoint URL and headers. For instructions, see [_](#step1-create-integration).
1. Configure your collector to send data to Grepr. For instructions, see [_](#configure-forwarding-to-grepr).

<Tabs items={['Datadog', 'Sumo Logic', 'Grafana Cloud', 'Amazon CloudWatch']}>
  <Tabs.Tab>

    To send OpenTelemetry data to Datadog from Grepr, configure your integration to use the Datadog OTLP endpoint and required headers.

    **Integration Configuration:**
    - **Endpoint URL**: `https://http-intake.logs.datadoghq.com/api/v2/logs`
    - **Headers**:
      - `dd-protocol`: `otlp`
    - **Secret Headers**:
      - `dd-api-key`: `<dd-api-key>`

    Replace `<dd-api-key>` with your Datadog API key.

    For more information, see [Datadog OTLP Logs Intake Endpoint](https://docs.datadoghq.com/opentelemetry/setup/intake_endpoint/otlp_logs/). To use Grepr's native Datadog integration instead of OpenTelemetry, see [Configure Datadog connections with a Grepr integration](/integrations/datadog).

  </Tabs.Tab>

  <Tabs.Tab>

    To send OpenTelemetry data to Sumo Logic from Grepr, configure your integration to use the Sumo Logic OTLP/HTTP source endpoint.

    **Integration Configuration:**
    - **Endpoint URL**: Your Sumo Logic OTLP/HTTP source URL. For example, `https://collectors.sumologic.com/receiver/v1/otlp/<sumo-unique-id>`. Replace `<sumo-unique-id>` with the unique identifier from your Sumo Logic OTLP/HTTP source.

    For more information, see [Sumo Logic's OTLP documentation](https://help.sumologic.com/docs/send-data/hosted-collectors/http-source/otlp/). To use Grepr's native Sumo Logic integration instead of OpenTelemetry, see [Configure Sumo Logic connections with a Grepr integration](/integrations/sumo-logic).

  </Tabs.Tab>

  <Tabs.Tab>

    To send OpenTelemetry data to Grafana Cloud from Grepr, configure your integration to use the Grafana Cloud OTLP endpoint and an access policy token.

    **Integration Configuration:**
    - **Endpoint URL**: Your Grafana Cloud OTLP endpoint. For example, `https://otlp-gateway-prod-us-west-0.grafana.net/otlp`.
    - **Secret Headers**:
      - `Authorization`: `Bearer <grafana-access-token>`

    Generate the Grafana access token from a Grafana Cloud Access Policy with write access to logs. To create a token, in your Grafana Cloud account, go to **Home > Administration > Users and access > Cloud access policies**.

    For detailed setup instructions, including configuration examples for Grafana Alloy, the OpenTelemetry Collector, and the Grafana Agent, see [_](/integrations/grafana).

  </Tabs.Tab>

  <Tabs.Tab>

    To send OpenTelemetry data to Amazon CloudWatch from Grepr, configure your integration to use the CloudWatch OTLP/HTTP endpoint, bearer token authentication, and JSON encoding.

    **Integration Configuration:**
    - **Endpoint URL**: `https://logs.<region>.amazonaws.com`
    - **Secret Headers**:
      - `Authorization`: `Bearer <bearer-token>`
    - **Headers**:
      - `x-aws-log-group`: `<log-group-name>`
      - `x-aws-log-stream`: `<log-stream-name>`
    - **Output encoding**: `JSON`

    The log group must have bearer token authentication enabled and the log stream must exist before you send logs.

    To learn more about integrating Grepr with CloudWatch, including configuration examples, see [_](/integrations/cloudwatch).

  </Tabs.Tab>
</Tabs>

## Security considerations

Grepr validates all headers you configure on an OpenTelemetry integration for potential security issues, including CRLF injection, control characters, and other attacks. Otherwise, when configuring OpenTelemetry integrations:

- Always use secret headers for sensitive information like API keys, tokens, or passwords.
- Ensure endpoint URLs use HTTPS for secure data transmission.
- Avoid using reserved headers. Some HTTP headers are reserved and cannot be set for security reasons.
