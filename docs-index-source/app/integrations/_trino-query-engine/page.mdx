# Query the Grepr data lake through your own Trino cluster

By default, Grepr uses Amazon Athena to run the queries behind Log Explorer, Trace Explorer, AI Actions, and the Grepr CLI's `query` command against your Grepr data lake. If you already operate a Trino cluster, you can configure a Trino query engine integration so these queries run against your Trino cluster instead. The Iceberg catalog and the SQL Grepr generates stay the same. Only the JDBC endpoint that executes the query changes.

You can use the Grepr UI or REST API to create a Trino query engine integration. To use the REST API, see the [Trino Query Engine Integration specification](/apis/api-spec#tag/Trino-Query-Engine-Integration).

## Requirements [#trino-requirements]

To use the Trino query engine integration, you need:

- The `TRINO_QUERY_ENGINE` feature enabled for your organization. This feature isn't enabled by default. Contact [support@grepr.ai](mailto:support@grepr.ai) to request it.
- A Trino cluster that Grepr can reach over the network, with a catalog configured against your organization's Grepr Iceberg data. To learn more about the Grepr data lake, see [The Grepr data lake](/grepr-platform/data-lake).

## Create a Trino query engine integration [#create-trino-integration]

To create a Trino query engine integration in the Grepr UI:

1. Go to the **Integrations** page in the Grepr UI and click **Add new** next to **Query Engines**.
1. In the **Add Trino Query Engine** dialog:
   - In the **Name** field, enter a name for the integration.
   - In the **Host** field, enter the hostname or IP address of your Trino coordinator. Don't include a scheme, such as `https://`, a path, or userinfo, such as `user@`.
   - In the **Port** field, enter the port for your Trino coordinator, a number from `1` to `65535`. The default port is `443`.
   - In the **Catalog** field, enter the name of the Trino catalog that's configured against your organization's Grepr Iceberg data. The catalog name can contain only letters, numbers, underscores, and hyphens, and must be 128 characters or fewer.
   - Use the **Connect over SSL/TLS** checkbox to turn SSL/TLS on or off when Grepr connects to your Trino cluster. This setting is on by default.
   - In the **User** field, enter the username to connect as. A username is always required, because Trino rejects any request that doesn't identify a user, even when your cluster doesn't require a password.
   - Optional: If your Trino cluster requires a password, enter it in the **Password** field. See [Set or update the integration password](#configure-password).
   - Optional: To pass additional Trino JDBC connection properties, click the plus icon (+) under **Extra properties**, then select a property and enter its value. See [Configure extra Trino connection properties](#extra-properties).
1. Click **Create**.

### Query engine integrations are limited to one per organization [#one-per-organization]

Unlike other integrations, a Trino query engine integration is global to your organization: it can't be scoped to a team, and your organization can have only one. Because every person in your organization must resolve the same query engine, scoping a Trino integration to a team, or allowing more than one, would let different people in your organization run the same query against different engines without knowing it. Keeping the integration global to the organization and limited to one keeps the choice of query engine unambiguous for everyone.

### Who can see and manage a Trino query engine integration [#visibility]

Because a Trino query engine integration is always organization-scoped, everyone in your organization can view it, regardless of team membership. You need edit permission on integrations at the organization level to create, update, or delete a Trino query engine integration, or to set its password. The stored password is never returned when the integration is read, regardless of permissions; it's always masked. See [Permissions in the Grepr platform](/grepr-platform/permissions).

## Set or update the integration password [#configure-password]

A Trino query engine integration's password is write-only. Grepr never returns the stored password: when you read the integration, the **Password** field is masked, showing only its last two characters so you can tell which credential is stored. Because a Trino query engine integration is visible to everyone in your organization, those two characters are visible to them as well.

In the Grepr UI, enter the password in the **Password** field when you create or edit the integration, and click **Create** or **Save**. When you edit an existing integration, leave the **Password** field blank to keep the current password unchanged.

If you're using the REST API, you can't set the password in the request body when you create or update the integration. Instead, set it with a dedicated endpoint:

```console
PUT /v1/integrations/trino-query-engine/{id}/password
```

Every Trino query engine integration has a `user` value, because `user` is required when you create or update one. To change the account a stored password belongs to, update the integration with a different `user` value. To remove the stored password entirely, delete the integration.

## Configure extra Trino connection properties [#extra-properties]

`extraProperties` is a set of additional Trino JDBC connection properties that Grepr passes to the driver unmodified. Grepr accepts only a fixed set of properties, and rejects an integration that includes any other property. Several other Trino JDBC properties can redirect the connection to a different host or supply credentials, such as an access token or a keystore path, and Grepr excludes those on purpose so that a data-lake configuration change can't silently change what the connection dials or authenticates with.

The following properties are allowed:

- `applicationNamePrefix`
- `clientTags`
- `clientInfo`
- `sessionProperties`
- `roles`
- `locale`
- `disableCompression`
- `explicitPrepare`
- `assumeNullCatalogMeansCurrentCatalog`
- `httpLoggingLevel`
- `SSLVerification`, restricted to `FULL` or `CA`
- `SSLTrustStoreType`, works only when paired with `SSLUseSystemTrustStore`
- `SSLUseSystemTrustStore`

<Callout type="warning">
  If you set `sessionProperties`, use the Trino JDBC driver's own format: a semicolon-separated list of `key:value` pairs, for example, `query_max_run_time:30m;query_priority:2`. This property uses a colon between the key and value, not an equal sign. Setting it with an equal sign, such as `query_max_run_time=30m`, produces an opaque connection error from the driver.
</Callout>

<Callout type="warning">
  `SSLVerification` accepts only `FULL` or `CA`. The Trino JDBC driver also supports `NONE`, but Grepr rejects it because the connection carries the integration's stored password, and turning off certificate verification would expose that password to a network attacker. If your Trino cluster's certificate doesn't match the hostname you connect with, for example, because you connect by IP address or through internal DNS, set `SSLVerification` to `CA` instead. `CA` still validates the certificate chain and only skips hostname matching.
</Callout>

<Callout type="warning">
  `SSLTrustStoreType` doesn't work on its own. The Trino JDBC driver only accepts a `SSLTrustStoreType` value when either `SSLTrustStorePath` or `SSLUseSystemTrustStore` is also set, and Grepr doesn't allow `SSLTrustStorePath`, because a trust store file path can redirect what the connection trusts. To trust an internal or private certificate authority, set `SSLUseSystemTrustStore` to `true`, and set `SSLTrustStoreType` only if your system trust store's format requires it. Supplying a trust store file isn't supported.
</Callout>

## Test the connection [#test-connection]

After you create a Trino query engine integration, you can test that Grepr can connect to your Trino cluster with the settings you configured.

In the Grepr UI, edit the integration and click **Test connection**. This button tests the currently saved connection, so save any changes before you click it.

To test the connection using the REST API, send a request to the following endpoint:

```console
POST /v1/integrations/trino-query-engine/{id}/test
```

This runs a trivial query against your configured Trino cluster and returns whether the connection succeeded, along with a message.

## How Grepr chooses a query engine [#query-engine-selection]

Athena is the default query engine for Log Explorer, Trace Explorer, AI Actions, and CLI queries. When the `TRINO_QUERY_ENGINE` feature is enabled for your organization and your organization has exactly one Trino query engine integration, Grepr automatically routes these queries to that integration instead. If your organization has no Trino query engine integration, Grepr continues to use Athena.

If Grepr can't determine how many Trino query engine integrations your organization has, or if your organization somehow has more than one, queries fail with an error instead of falling back to Athena. Grepr fails this way on purpose: silently falling back to Athena would run your query against an engine you didn't choose, which could return different results depending on how each engine is configured.

### Override the query engine from the CLI [#cli-query-engine]

The Grepr CLI selects the query engine for the `query` command using the `GREPR_QUERY_ENGINE` environment variable, which accepts `athena`, `flink`, or `trino`.

An explicit value always wins over automatic discovery:

- Setting `GREPR_QUERY_ENGINE=athena` runs your query against Athena, even if your organization has a Trino query engine integration configured.
- Setting `GREPR_QUERY_ENGINE=trino` requires your organization to have exactly one Trino query engine integration. If it doesn't, the command fails.

<Callout type="info">
  There is no command-line option for selecting the query engine. Use the `GREPR_QUERY_ENGINE` environment variable instead.
</Callout>

If you don't set `GREPR_QUERY_ENGINE`, the CLI discovers the query engine the same way Log Explorer, Trace Explorer, and AI Actions do: it uses Trino when the `TRINO_QUERY_ENGINE` feature is enabled and your organization has exactly one Trino query engine integration, and uses Athena otherwise. As with the UI, a failed lookup or more than one Trino query engine integration causes the command to fail rather than fall back to Athena.

To set the environment variable for a single command:

```console copy
GREPR_QUERY_ENGINE=trino grepr query \
  --dataset-id <dataset-id> \
  --start 2026-02-26T00:00:00Z \
  --end 2026-02-26T23:59:00Z \
  --query "level:ERROR"
```

To learn more about the Grepr CLI, see [The Grepr CLI](/cli).

## Limitations

- Your organization can have only one Trino query engine integration, and it can't be scoped to a team. See [Query engine integrations are limited to one per organization](#one-per-organization).
- The Trino query engine integration authenticates to your Trino cluster with a username and password only. It doesn't support token-based, OAuth, or Kerberos authentication.
- Grepr doesn't limit the amount of data a query can scan when it runs against a Trino query engine integration. A query timeout is the only limit. This differs from the default limits Grepr enforces for Athena queries. See [The Grepr data lake](/grepr-platform/data-lake).
