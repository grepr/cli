# Configure MCP server connections with a Grepr integration

An MCP integration connects Grepr to a Model Context Protocol server, or MCP server, run by another system. After you create one, you can let a Grepr AI agent call the tools that server publishes, so the agent gains capabilities, such as reading an incident, querying a dashboard, posting to a channel, or opening a pull request.

<Callout type="info">
  MCP integrations, along with the rest of the Grepr AI agent features, are in a closed beta. To request access, contact [support@grepr.ai](mailto:support@grepr.ai).
</Callout>

<Callout type="warning">
  This page is about Grepr calling another system's MCP server. For the opposite direction, where an AI agent, such as Claude, calls Grepr's own MCP server, see [_](/apis/mcp).
</Callout>

## Requirements

To create an MCP integration, you need:

- A credential for the system you are connecting. See [Create an MCP integration](#create) for where to get it.

## What an agent can do through a connected server [#server-tools]

The tools an agent gains depend on the server you connect:

| Type | What an agent can do with it |
|---|---|
| Datadog MCP | Read monitors, dashboards, logs, and metrics from your Datadog organization. |
| GitHub MCP | Read and change repository content, issues, pull requests, and workflow runs. |
| Jira MCP | Read, search, comment on, create, transition, and assign issues on your Jira Cloud site. |
| PagerDuty MCP | Read and act on incidents, services, and schedules. |
| Slack MCP | Read and post messages in the channels the token can reach. |

Each integration has a server URL you set, so you can point one at a self-hosted or regional endpoint rather than the vendor's. The Jira MCP and Slack MCP are the exceptions. The Jira MCP's server URL must be on `mcp.atlassian.com`, so Grepr sends its credential only to Atlassian. The Slack MCP always uses Slack's MCP server, `https://mcp.slack.com/mcp`, so its form has no server URL field, and Grepr sends the token only to Slack.

Don't see an MCP in the list? Send a request to [support@grepr.ai](mailto:support@grepr.ai).

## Create an MCP integration [#create]

1. On the **Integrations** page, next to the **MCP Servers** section heading, click **Add new**.
1. In the **Add MCP Server** dialog, select the server from the **Type** menu.
1. Complete the remaining fields, which depend on the type you selected.
1. Click **Create**.

You cannot change an integration's type after you create it. You can change its other fields at any time, and each investigation picks up the change when it starts.

![The Add MCP Server dialog for a Datadog MCP integration, showing the type, name, server URL, and credential fields.](/images/integrations/mcp/add-mcp-server.png)

Every type has a **Name** field, which identifies the integration when you configure an agent. Every type except the Slack MCP also has an **MCP Server URL** field. The remaining fields are the credential the server authenticates with.

The credential decides what the agent can do through that MCP. Grepr passes it through as you supply it, so give the token minimal access for what the agent needs. Select the tab for the MCP you are connecting.

<Tabs items={['Datadog MCP', 'GitHub MCP', 'Jira MCP', 'PagerDuty MCP', 'Slack MCP']}>
  <Tabs.Tab>

    | Field | Value |
    |---|---|
    | **MCP Server URL** | `https://mcp.datadoghq.com/v1/mcp`, or your regional Datadog MCP endpoint. |
    | **API Key (DD-API-KEY)** | A Datadog API key. |
    | **Application Key (DD-APPLICATION-KEY)** | A Datadog application key. |

    Create both keys in Datadog under **Organization Settings**. An application key carries the authorization scopes that decide what the agent can read, so scope it to the data you want the agent to reach, such as monitors, dashboards, and logs. To learn more, see [API and Application Keys](https://docs.datadoghq.com/account_management/api-app-keys/) and [Authorization Scopes](https://docs.datadoghq.com/api/latest/scopes/) in the Datadog documentation.

    If you already use Datadog as a Grepr source or sink, this is a separate integration. Reusing the same keys is fine. See [_](/integrations/datadog).

  </Tabs.Tab>

  <Tabs.Tab>

    | Field | Value |
    |---|---|
    | **MCP Server URL** | `https://api.githubcopilot.com/mcp/`, or your GitHub Enterprise MCP endpoint. |
    | **Personal access token** | A GitHub personal access token. |

    Create the token in GitHub under **Settings** > **Developer settings** > **Personal access tokens**. A fine-grained token is the better choice, because you can limit it to the repositories the agent works in.

    Grant the token access to the repository content, issues, pull requests, and workflow runs the agent needs. An agent that only reads code needs read access alone, and an agent that opens pull requests needs write access to contents and pull requests. To learn more, see [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-secure/managing-your-personal-access-tokens) in the GitHub documentation.

  </Tabs.Tab>

  <Tabs.Tab>

    | Field | Value |
    |---|---|
    | **MCP Server URL** | `https://mcp.atlassian.com/v2/mcp?tools=all`. |
    | **Jira site URL** | The web URL of your Jira Cloud site, such as `https://<your-site>.atlassian.net`. It must be an HTTPS URL. |
    | **Service account API token** | An API token of an Atlassian service account. Grepr sends it as a Bearer token. |

    The Jira MCP connects to the Atlassian Rovo MCP server. This server supports Jira Cloud only. It does not support Jira Data Center.

    Before you create the integration, do these steps in Atlassian:

    1. An Atlassian organization admin must turn on API token authentication for the Rovo MCP server. In Atlassian Administration, go to **Connectors** > **Atlassian MCP server** > **Authentication**, and select **Allow API token authentication**.
    1. Create a service account for the agent. Give it the **User** role on the Jira app of your site.
    1. Create an API token for the service account with these scopes: `read:jira:agent-interface`, `search:jira:agent-interface`, and `write:jira:agent-interface`.
    1. Give the service account access only to the Jira projects the agent needs. Do not give it access to Jira Service Management projects, because a comment there can go to your customers by email.

    A new Jira MCP integration on an agent can only read until someone turns on its write tools. After that, an investigation runs those tools with no approval step, and the logs and alerts it reads can contain text that tries to steer the agent. The projects and scopes of the service account are what limit the agent. Keep the token to the three scopes above. With more scopes, **All tools** on an agent also gives Confluence, Compass, or delete tools.

    When you save the API token, Grepr checks it with Atlassian. Grepr stores the token only when Atlassian accepts it and it gives access to Jira tools.

    Grepr uses the **Jira site URL** to make links to the issues that an agent creates, comments on, transitions, or edits. An action has a link only when the Atlassian result names the issue key.

    | Field | Value |
    |---|---|
    | **MCP Server URL** | `https://mcp.pagerduty.com/mcp`, or your PagerDuty MCP endpoint. |
    | **Account URL** | Your PagerDuty account URL, such as `https://<your-org>.pagerduty.com`. Optional. |
    | **API Key** | A PagerDuty API key. |

    Create the key in PagerDuty under **Integrations** > **API Access Keys**. A read-only key lets an agent read incidents, services, and schedules, and a full-access key also lets it acknowledge or resolve incidents, so choose the one that matches what you want the agent to do. To learn more, see [API Access Keys](https://support.pagerduty.com/main/docs/api-access-keys) in the PagerDuty documentation.

    Grepr uses the **Account URL** to build links back to incidents in the actions an agent records, so set it if you want those links to resolve.

  </Tabs.Tab>

  <Tabs.Tab>

    | Field | Value |
    |---|---|
    | **Token** | A Slack bot token, which begins with `xoxb-`, or a Slack user token, which begins with `xoxp-`. To read and post as a Slack app, use a bot token. See [Connect Slack as an app](#slack-bot). |

    With a user token, the agent acts as the Slack user who owns the token, and it posts as that user. It can post in the channels that user is a member of, including Slack Connect channels that your workspace shares with another organization, and in direct messages. The token's scopes decide what the agent can read.

    To let an agent post to a channel as a Slack user:

    1. Create a Slack user for the agent, such as `Grepr Agent`. With a dedicated user, the agent's messages do not show as a person's.
    1. Sign in to Slack as that user. Go to [Slack apps](https://api.slack.com/apps?new_app=1). In the **Create new app** dialog, select **Paste a manifest** and click **Continue**. Then select your workspace and paste this manifest:

       ```yaml
       display_information:
         name: Grepr Agent
       oauth_config:
         scopes:
           user:
             - chat:write
       settings:
         is_mcp_enabled: true
         token_rotation_enabled: false
       ```

       The manifest turns on Slack's MCP server for the app and grants only `chat:write`, which the agent needs to post. To let the agent read the replies in its threads, also add `channels:history` for public channels and `groups:history` for private channels. With `channels:history`, the agent can read every public channel in your workspace, including channels its user is not in. With `groups:history`, it can read only the private channels its user is in.

    1. Install the app to your workspace as the agent's user and allow the scopes. If your workspace requires app approval, request it, and install the app after a Slack admin approves it. Do not turn on public distribution or token rotation. Slack's MCP server accepts a token only from an app that is internal to your workspace or listed in the Slack Marketplace. Grepr does not refresh the token, and a rotated token expires after 12 hours.
    1. On the app's **OAuth & Permissions** page, copy the **User OAuth Token**.
    1. Add the agent's user to the channel the agent posts to, such as with `/invite @Grepr Agent`. A new Slack user joins your workspace's default channels, so have the user leave the ones the agent does not post to. The user cannot leave your workspace's general channel, so the agent can post there unless a workspace owner or admin restricts who can post in it.
    1. Copy the channel ID. In Slack, click the channel name. The ID is at the bottom of the **About** tab.
    1. In Grepr, create a Slack MCP integration and enter the user token in the **Token** field. See [Create an MCP integration](#create).
    1. Enable the integration on the agent. A new integration on an agent starts with all of the server's tools allowed. To limit the agent to posting, edit its allowed tools, select **Only the tools I choose**, and select `slack_send_message`. See [Choose which tools an agent can call](#allowed-tools).
    1. In the agent's system prompt, give the channel ID and tell the agent when to post, such as `Post a summary of each investigation to Slack channel C0123456789.` See [_](/ai-agents/create-an-agent#system-prompt).

    An investigation runs Slack tools with no approval step, and the logs and alerts it reads can contain text that tries to steer the agent. The channels the agent's Slack user is in, the token's scopes, and the agent's allowed tools are what limit the agent. Channel membership does not limit direct messages. A message the agent posts to a Slack Connect channel reaches the other organization.

    To learn more about Slack tokens, see [Access tokens](https://docs.slack.dev/authentication/tokens) in the Slack documentation.

### Connect Slack as an app with a bot token [#slack-bot]

A Slack MCP integration takes a bot token or a user token. With a bot token, the agent works as a Slack app. With a user token, the agent acts as a Slack user.

Slack's MCP server accepts only user tokens, so with a bot token Grepr provides the agent's Slack tools:

| Tool | What it does |
|---|---|
| `slack_send_message` | Posts a message in a channel, or a reply in a thread. |
| `slack_read_channel` | Reads the recent messages of a channel. |
| `slack_read_thread` | Reads a thread: its first message and its replies. |

The app reads and posts only in the channels that it is a member of. It can also send a direct message to a member of your workspace. You do not need a Slack user for the agent, so the agent does not use a Slack seat or join your default channels.

Use a user token when the agent needs other Slack tools, such as search.

To let an agent read and post in a channel as a Slack app:

1. Go to [Slack apps](https://api.slack.com/apps?new_app=1). In the **Create new app** dialog, select **Paste a manifest** and click **Continue**. Then select your workspace and paste this manifest:

   ```yaml
   display_information:
     name: Grepr Agent
   features:
     bot_user:
       display_name: Grepr Agent
       always_online: false
   oauth_config:
     scopes:
       bot:
         - chat:write
         - channels:history
         - groups:history
   settings:
     token_rotation_enabled: false
   ```

   The manifest grants `chat:write` to post, `channels:history` to read public channels, and `groups:history` to read private channels. With either history scope, the app reads only the channels that it is a member of. For an agent that only posts, remove the two history scopes. Do not add `chat:write.public`. With that scope, the app can post in every public channel, including the channels that it is not a member of.

1. Install the app to your workspace. If your workspace requires app approval, request it, and install the app after a Slack admin approves it. Do not turn on token rotation. Grepr does not refresh the token, and a rotated token expires after 12 hours.
1. On the app's **OAuth & Permissions** page, copy the **Bot User OAuth Token**, which begins with `xoxb-`. When you save it in Grepr, Grepr checks it with Slack: Slack must accept it as a bot token, and the app must have `chat:write`. Grepr stores the token only when it passes.
1. Add the app to each channel that the agent reads or posts in, such as with `/invite @Grepr Agent` in the channel.
1. Copy the channel ID. In Slack, click the channel name. The ID is at the bottom of the **About** tab.
1. In Grepr, create a Slack MCP integration and enter the bot token in the **Token** field. See [Create an MCP integration](#create).
1. Enable the integration on the agent. See [Choose which tools an agent can call](#allowed-tools).
1. In the agent's system prompt, give the channel ID and tell the agent when to post, such as `Post a summary of each investigation to Slack channel C0123456789.` See [_](/ai-agents/create-an-agent#system-prompt).

The app can read and post in a Slack Connect channel that your workspace shares with another organization. A member of your organization adds the app to the channel, and the other organization does not approve it. If the other organization owns the channel and lets your organization only post, you cannot add the app. A message that the agent posts in a Slack Connect channel reaches the other organization.

An investigation runs Slack tools with no approval step, and the logs, alerts and Slack messages it reads can contain text that tries to steer the agent. The channels that the app is a member of limit where the agent reads and posts. Channel membership does not limit direct messages, so the app can also send a direct message to a member of your workspace.

To change an existing Slack MCP integration to a bot token, edit the integration and enter the bot token in the **Token** field. The agents that use the integration keep it. With a bot token, an agent can call only the three tools above. If an agent's allowed tools do not name them, edit its allowed tools and select the Slack tools that the agent needs.

## Choose which tools an agent can call [#allowed-tools]

Creating an integration does not give any agent access to it. You enable an integration on each agent, and you choose which of the server's tools that agent can call. Two agents can therefore share one integration with different tool allowances.

The tool allowance lives on the agent, not on the integration. To set it, go to the agent's **Capabilities** step, find the integration in the **MCP integrations** table, and edit its allowed tools. Grepr reads the tool list from the server, marks each tool as read only or writing, and lets you allow all tools or only the ones you select. To learn more, see [_](/ai-agents/capabilities#mcp-integrations).

When you enable a Jira MCP integration on an agent, its allowed tools start as a set that only reads: it gets, searches, and lists Jira issues, comments, change history, and transitions. To let the agent comment on, create, transition, or edit issues, edit its allowed tools, select **Only the tools I choose**, and select the tools marked **Writes** that you want, such as `addOrEditJiraIssueComment`, `createJiraIssue`, `transitionJiraIssue`, or `editJiraIssue`.

An agent can enable at most one GitHub MCP integration. The agent's `github_code` tool also requires an enabled GitHub MCP integration, because that is how it reaches source code.
